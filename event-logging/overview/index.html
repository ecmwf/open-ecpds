    Event Logging in OpenECPDS¶

    OpenECPDS generates structured event logs that capture key activities and transitions within the system, including data retrieval, replication, and dissemination processes. These events are available through both structured file logging and native OpenTelemetry export, providing insight into operations and supporting troubleshooting at different stages of the workflow.

    At ECMWF, different platforms use Splunk and Fluent Bit pipelines. The structured file output supports existing Splunk collection and analysis, while native OpenTelemetry exports events over OTLP to compatible collectors, including Fluent Bit with an OTLP input configured. Both outputs can be enabled independently or used together. OpenTelemetry also supports correlation with application traces and metrics.

    OpenECPDS is not tied to a particular backend: file collectors and OTLP-compatible pipelines can route events into each organisation's monitoring and analytics ecosystem.

    File logs can be found in the directories mounted to the containers — see Checking the Containers and Logs.

    Structure, format and standards

    The splunk.log events are structured logs in an application-specific encoding. A custom encoding is not the same as an absence of structure. The following distinctions apply to both the file output and native OpenTelemetry:

    Criterion What it means How splunk.log meets it
    Identifiable fields Consumers can distinguish the event category and individual named fields. Each record starts with a category code, followed by ordered Name=value fields separated by ;.
    Consistent semantics A field has a defined meaning within its event category. Category-specific field definitions describe identifiers, outcomes, timestamps, sizes and other event attributes.
    Documented schema Consumers know which fields to expect and how to interpret them. Each event-category page provides a Fields table with names, types and meanings, alongside example records.
    Defined value types Values can be interpreted as timestamps, booleans, integers or strings according to the schema. The file represents values as text; consumers apply the documented types. Native OpenTelemetry preserves supported numeric and boolean attribute types directly.
    Unambiguous field boundaries Data cannot be mistaken for separators or extra records. File records containing ;, CR or LF in a category, field name or value are rejected with a WARN rather than written ambiguously. Field names cannot contain =; parsers split each Name=value field at its first =, preserving equals signs within values.
    Defined record boundaries Consumers can identify where one event ends and the next begins. Each accepted event occupies one line. Embedded CR/LF is rejected for the file output.
    Machine processing Fields can be extracted consistently without interpreting free-form prose. A parser reads the category, splits fields on ;, then splits each field at its first = and applies the category schema. File collection supports existing Splunk forwarder pipelines.
    Standardisation The encoding and schema may be application-specific or defined by an external specification. The semicolon-delimited encoding and ECPDS event schema are application-specific, not a claim of JSON, syslog or OTLP conformance. Native OpenTelemetry provides the alternative standard telemetry data model and OTLP export; ECPDS-specific event attributes remain application-defined.

    A flat, single-line representation does not remove event structure, and nesting is not required for structured logging. Likewise, using familiar value types does not make an application-specific encoding an external standard. Structure, encoding, schema and standardisation are related but separate properties.

    The practical trade-off is interoperability: existing Splunk pipelines can continue using their established file parser, whereas other consumers must implement that parser or use native OpenTelemetry. A Splunk forwarder can collect other file encodings too; the current format is an integration choice, not a requirement imposed by Splunk.

    Delimiter validation protects the file representation without modifying values or changing its established encoding. A rejected file record is absent from splunk.log; its native OpenTelemetry event can still be emitted when that output is enabled. This is an encoding safeguard, not a guarantee of delivery or a substitute for monitoring collection failures.

    Reading the examples¶

    Each event-category page has Splunk (splunk.log) and OpenTelemetry tabs showing the same event and sample field values. The shared Fields table describes both outputs. The examples are illustrative, not captured production records; existing sample timestamps are retained and do not necessarily describe a chronological transfer lifecycle.

    The OpenTelemetry tab is a simplified Collector/backend representation, not the raw OTLP payload. Actual export uses OTLP and batches records with resource and instrumentation-scope metadata. OTLP JSON, when used for inspection, has additional wrappers such as stringValue, intValue and boolValue; backend field layout can differ. Resource attributes such as service.version and SDK metadata are omitted from the examples for readability.

    Unlike the semicolon-separated file output, telemetry attributes retain their application types: counts and sizes are numbers, flags are booleans, and textual identifiers remain strings even if they contain only digits. Timestamp-valued event attributes retain their formatted string representation. The TimeStamp value represents an absolute instant. In OpenTelemetry, the log record's top-level timestamp is set from that instant and is timezone-independent; backends commonly display it in UTC. The TimeStamp attribute itself, like the legacy Splunk field, is formatted without a UTC offset using the Master JVM's default timezone. The examples assume that timezone is UTC, so their attribute value and top-level timestamp show the same wall-clock time. Prefer the top-level OpenTelemetry timestamp for cross-service correlation; a timezone-less TimeStamp string cannot identify its timezone by itself. Durations remain milliseconds where specified by the Fields table. These records all use log severity INFO, including the ERR and DEA categories: the category and event fields describe the operational outcome.

    Telemetry metadata Meaning
    resource.service.name Exporting service; defaults to open-ecpds-master.
    resource.service.instance.id Master identity, normally derived from [Login] root or hostName.
    scope.name ecmwf.ecpds.operational-events, the instrumentation scope.
    eventName / body ecpds.<category> / <category>, for example ecpds.PRS / PRS.
    attributes.ecpds.event.id Generated UUID identifying the telemetry event; useful for deduplicating journal retries.
    attributes.ecpds.event.category The category code, matching the file output's first field.
    attributes.ecpds.transfer.attempt.id Present on attempt-aware UPH/ERR events when a valid transfer context is available; distinguishes attempts of the same transfer.
    attributes.ecpds.retrieval.id Present on RET events when retrieval tracing supplies a valid retrieval context; links all related transfer records for the same DataFile retrieval.
    traceId, spanId Optional valid trace context linking a log to a span; a corresponding trace is not guaranteed to be sampled or retained.

    The UPH example illustrates optional correlation. Product-status (PRS), retrieval (RET), incoming-history (INH), copy (CPY) and denied-access (DEA) events are not automatically assigned a dissemination-attempt context simply because they describe a file or contain a transfer ID. INH logs for actual portal uploads/downloads can instead link to a portal-transfer span. See Transfer traces and log correlation for tracing scope and configuration.

    Choosing event outputs¶

    The Master publishes the same operational events through two independent outputs:

    • Splunk file: the SplunkLogs Log4j2 logger writes splunk.log. Records use category codes and ordered text fields; Log4j2 controls file rotation. A category, field name or value containing a semicolon, carriage return or newline causes the entire file record to be rejected with a WARN in the Master service log. Field names containing = are also rejected; values may contain = (split each field at its first equals sign). Warnings do not include offending content. This validation does not reject the independent native OpenTelemetry event or interrupt application operations.
    • Native OpenTelemetry: the application supplies named, typed attributes directly to an OpenTelemetry Logs SDK. It does not tail or parse splunk.log. Records are exported over OTLP to a Collector or compatible platform.

    Configure the Master in etc/master/conf/ecmwf.properties:

    [OperationalEvents]
splunkEnabled=yes
openTelemetryEnabled=no
    Required output splunkEnabled openTelemetryEnabled
    Neither no no
    Splunk file only (default) yes no
    OpenTelemetry only no yes
    Both yes yes

    Restart the Master after changing these settings or the OpenTelemetry configuration. These switches control operational event output only: ordinary service logs, database history and the Monitor change log are unaffected. Log4j2 may create an empty splunk.log file when its appender starts.

    The file output also honours the SplunkLogs INFO logging level. Disabling that logger does not disable OpenTelemetry. Event-specific gates still apply to both outputs, including the transfer's recordUPH selection and the Data User's portal.recordSplunk and portal.triggerEvent settings. The portal.recordSplunk setting controls INH event generation, not selection of the output platform.

    OpenTelemetry connection¶

    Enable openTelemetryEnabled and supply standard OpenTelemetry environment variables to the Master process. For a service installation, put connection settings in /etc/ecpds/master.cnf, which the Master launcher sources:

    export OTEL_EXPORTER_OTLP_ENDPOINT="https://collector.example.org:4318"
export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
export OTEL_EXPORTER_OTLP_TIMEOUT="10000"
# Optional private Collector CA:
# export OTEL_EXPORTER_OTLP_CERTIFICATE="/etc/ecpds/master/collector-ca.pem"

    Use export for each environment setting in master.cnf so Java inherits it. Any supported OTEL_* setting can be supplied this way without editing the launcher. Headers stay in the environment rather than the launcher's generated JVM argument file.

    The Master's ecmwf.properties contains output switches and the journal owner in [OperationalEvents], and batching defaults in:

    [OpenTelemetry]
logsMaxQueueSize=2048
logsMaxExportBatchSize=512
logsScheduleDelayMillis=1000

    Precedence for these batching settings is JVM system properties → environment variables → ecmwf.properties → built-in defaults. Their standard overrides are otel.blrp.max.queue.size / OTEL_BLRP_MAX_QUEUE_SIZE, otel.blrp.max.export.batch.size / OTEL_BLRP_MAX_EXPORT_BATCH_SIZE, and otel.blrp.schedule.delay / OTEL_BLRP_SCHEDULE_DELAY. Delay is in milliseconds. These settings are optional; the values shown above are the defaults. With journaling enabled, the database is the normal pending queue. These settings tune only the bounded, in-memory fallback queue used when persistence fails; they do not limit the database backlog. With journaling disabled, they tune the normal in-memory log queue. Restart the Master after changes. The SDK does not read arbitrary OTEL_* keys from ecmwf.properties.

    For containers, pass these variables through the container environment, or mount master.cnf at the path above. JVM system properties such as -Dotel.exporter.otlp.endpoint=... are also supported through JAVA_OPTS. Merely setting variables in the host shell does not pass them into an existing container or systemd service.

    The default protocol is http/protobuf; without an endpoint override its SDK default is the local Collector at http://localhost:4318/v1/logs. Set OTEL_EXPORTER_OTLP_PROTOCOL=grpc to use a gRPC receiver with an appropriate endpoint, normally port 4317 and no /v1/logs suffix. A logs-specific HTTP endpoint must include the full path; the generic OTEL_EXPORTER_OTLP_ENDPOINT instead supplies a base URL. For HTTP/protobuf, the SDK appends /v1/logs to that base URL. Logs-specific settings override their generic counterparts when both are configured. The Master service name defaults to open-ecpds-master; OTEL_SERVICE_NAME is an optional override.

    For authentication, inject OTEL_EXPORTER_OTLP_HEADERS through your secret management system. For a private Collector CA, use the SDK's OTEL_EXPORTER_OTLP_CERTIFICATE setting. Use HTTPS for non-local traffic; do not disable certificate validation. Never commit credentials to configuration or include authorization headers in diagnostic output.

    Transfer tracing is enabled independently as described below; neither output replaces Prometheus/JMX metrics. Standard OTEL_LOGS_EXPORTER settings apply, with otlp as the default. Invalid SDK configuration prevents startup rather than silently falling back to another output. When OpenTelemetry is disabled, its exporters are not initialized.

    Transfer traces and log correlation¶

    Optional distributed traces follow one scheduled dissemination attempt, not the lifetime of a file or its complete retry history. Enable them in [OpenTelemetry] in the Master's ecmwf.properties:

    [OpenTelemetry]
tracesEnabled=yes
tracesSampleRatio=0.01
tracesMaxQueueSize=2048
tracesMaxExportBatchSize=512
tracesScheduleDelayMillis=1000

    Restart the Master after changes. Tracing is off by default and is independent of [OperationalEvents] openTelemetryEnabled: traces can be exported without native logs, and logs can be exported without traces. To use both, enable both switches on the Master. Movers automatically follow the tracing decision supplied with each transfer. No OpenTelemetry settings, Collector credentials or direct Collector connections are required on Movers or Continental relays.

    Use the generic OTLP connection settings above in master.cnf. Only the Master exports logs and traces to the Collector. With HTTP/protobuf the base endpoint supplies /v1/traces for spans and /v1/logs for logs. If a platform has separate ingest URLs, set OTEL_EXPORTER_OTLP_TRACES_ENDPOINT and OTEL_EXPORTER_OTLP_LOGS_ENDPOINT to the full signal-specific URLs. Service names default to open-ecpds-master and open-ecpds-mover; Mover spans retain their originating service and instance identity.

    Movers send completed spans asynchronously in batches through their existing Master connection. Continental Movers use the existing REST relay path. Forwarding queues are bounded and held in memory; connection failures are retried while the process is running, but full queues and shutdown can discard spans. Check Mover, relay and Master service logs for forwarding/export errors. Trace forwarding does not block transfers. Deploy the Master, Movers and Continental relays together when enabling retrieval traces so all components recognize the retrieval-span wire format.

    Traces cover dispatch, transfer execution and completion for dissemination attempts. Retries have separate traces. UPH and dissemination ERR native logs include OTLP trace_id and span_id fields linking to the relevant span; ecpds.transfer.attempt.id also identifies the attempt. Retrieval tracing is also optional and independent of [OperationalEvents] openTelemetryEnabled: when enabled, one trace follows a Master retrieval of a DataFile, including each remote Mover attempt and the Mover-side download span. Retries across Movers appear in that same retrieval trace. Each successful RET log for transfers related to the DataFile shares the trace context and ecpds.retrieval.id; unsuccessful retrievals have error spans but do not emit RET logs. Acquisition directory discovery is not covered by retrieval traces. Actual portal uploads and downloads have a separate Master-side ecpds.portal.transfer span; its recorded interval, byte count, protocol and server come from the completed transfer's protocol event. The associated OpenTelemetry INH log carries that span's trace context; multiple INH records for one portal operation share its span. The scheduled INH action records an ecpds scheduling request, not a file transfer, and is not traced. These portal spans use the same Master tracing configuration and sampling. Apply access controls and retention to tracing data as well as logs.

    The default sampler is parent-based trace-ID ratio sampling: the Master samples approximately 1% of attempts and Movers honour that decision. Set tracesSampleRatio=1.0 for all attempts, or 0.0 for none. Standard OTEL_TRACES_SAMPLER / OTEL_TRACES_SAMPLER_ARG override these defaults; retain a parent-based sampler. OTEL_BSP_MAX_QUEUE_SIZE, OTEL_BSP_MAX_EXPORT_BATCH_SIZE and OTEL_BSP_SCHEDULE_DELAY override the corresponding trace batching defaults, with JVM -Dotel.* properties taking precedence over environment values. The delays are in milliseconds. OTEL_TRACES_EXPORTER defaults to otlp; OTEL_SDK_DISABLED also applies.

    Trace delivery is best effort and is not database-journalled. Bounded queues, Collector outages, crashes or abrupt shutdown can lose spans. Export failures are reported in service logs. A linked log may have no corresponding stored trace because of sampling, export failure or trace retention. Log delivery and transfer success do not depend on trace delivery.

    OpenTelemetry metrics¶

    Master application metrics are optional and independent of native logs and traces. Enable them in [OpenTelemetry]:

    [OpenTelemetry]
metricsEnabled=yes
metricsExportIntervalMillis=60000
metricsExportTimeoutMillis=30000

    They use the same OTLP connection settings as logs and traces, but a separate SDK/provider. Metrics do not replace the existing Prometheus/JMX JVM and MBean export. The first application instruments cover transfer dispatch/completion, retrieval attempts/completion, and actual portal transfers, with counters and duration/byte histograms. Transfer outcomes and portal direction use bounded attributes; transfer, file, user, destination and host IDs are never metric labels. The SDK can attach trace-based exemplars to recorded measurements when the associated operation has a sampled trace. Counts and histograms are recorded independently of trace sampling.

    Observable gauges reuse Master-side sources behind the Live ECPDS Earth KPIs: rolling 24-hour transferred bytes by Host Type, open Data Portal sessions and rolling portal upload/download rates, and cached DataMover storage used and capacity. The storage aggregation uses the same per-Mover cache snapshot as the globe. Active transfer count, distinct-host and throughput gauges are emitted only while live transfer sampling is enabled by an interested globe client; absence of these gauge points means the feed is not currently sampling, not that there are no active transfers.

    The SDK exports OTLP metrics by default when enabled. Standard OTEL_METRIC_EXPORT_INTERVAL and OTEL_METRIC_EXPORT_TIMEOUT (or corresponding otel.metric.export.* JVM properties) override the interval and timeout in ecmwf.properties. Metrics export is best effort and is not journalled.

    Native record schema¶

    Each record has:

    • Event name ecpds.<category>, for example ecpds.UPH, and body UPH.
    • Attribute ecpds.event.category containing the category code.
    • Attribute ecpds.event.id identifying the event; journal retries preserve it.
    • The field names listed below as attributes, preserving their original case. Booleans and integral/floating-point Java values use native OTLP types; textual fields remain strings. The none, - and null placeholders retain their textual meaning.
    • The original TimeStamp as the log timestamp and as a textual attribute. The top-level timestamp represents the absolute instant; the attribute uses the Master JVM's default timezone and has no zone suffix. Other date/time fields use their category's textual formatting and may likewise omit a zone.
    • Resource fields service.name (default open-ecpds-master), service.version, and service.instance.id identifying the Master. Explicit OTEL_RESOURCE_ATTRIBUTES values can override the version and instance defaults.

    Values containing semicolons or equals signs remain individual native attributes; they are not split into text fields. OpenTelemetry SDK attribute limits still apply. Treat filenames, user identifiers, addresses, comments and other event fields as potentially sensitive and apply appropriate Collector access controls, filtering and retention. No full configuration snapshot or password/token field is included in these records.

    Delivery and failure handling¶

    Without database journaling, delivery uses a bounded in-memory queue and is best effort. A full queue, export failure or process shutdown can lose records; retries may also create duplicates. Check the Master service log and Collector diagnostics for delivery errors. For stronger durability, enable the database journal, enable the Splunk file and/or use a local Collector with persistent queues, and monitor the pipeline's health. The outputs are independent, not automatic failover: OpenTelemetry failure does not turn file logging on if it was disabled.

    Durable database journal¶

    For recovery during endpoint outages and Master restarts, enable the optional database journal. It stores each native event before attempting delivery, not only after an export has already failed. The splunk.log output remains independent and is not replayed by this feature.

    Journaling requires the OPERATIONAL_EVENT table in the Master's database, included in the supplied installation schema. The running service does not create tables. Deploy the supplied Master SQL files and Monitor pages.

    Then configure and restart the Master:

    [OperationalEvents]
splunkEnabled=yes
openTelemetryEnabled=yes
journalEnabled=yes
journalOwner=production-master

    Supply the OTLP endpoint, authentication and TLS settings as described above. Journal mode requires OTEL_LOGS_EXPORTER=otlp (the default), with one OTLP exporter. To fan out to several platforms, use a Collector downstream. Setting OTEL_SDK_DISABLED=true while journaling is enabled is a configuration error, rather than silently bypassing persistence.

    Keep journalOwner stable and unique to the logical Master. If omitted, it defaults to Login.root, then Login.hostName, then master. Only that owner's records are replayed. A failover instance must use the same owner and database, with the previous instance stopped; run only one active Master per owner. Changing the owner leaves the previous owner's pending rows untouched.

    Persisted events are retained until export is acknowledged and are retried after failures or Master restarts. Retries can produce duplicates; use ecpds.event.id for downstream deduplication.

    In journal mode, the database is the pending queue: OTEL_BLRP_* settings apply only to the best-effort fallback path, not to normal journal delivery. Shutdown need not drain the database; the next start resumes pending work. Disabling OpenTelemetry or journaling pauses replay without deleting pending rows. Re-enabling it with the same owner resumes replay.

    Guarantees and operational limits¶

    • Endpoint outages: successfully persisted, unacknowledged events have no automatic expiry or retry limit, including permanent HTTP errors. Fix the endpoint or credentials; an indefinitely rejected batch can block the backlog. An undecodable row is also retained with an error for operator investigation.
    • Database failures: operations continue, a prominent rate-limited DATABASE EVENT JOURNAL UNAVAILABLE error reports persistence failures, and the application attempts best-effort delivery through the SDK's memory queue. Those events are not guaranteed durable and are not automatically backfilled later. An ambiguous database acknowledgement can also result in a persisted record and a best-effort delivery of the same event.
    • Acknowledgements: an OTLP acknowledgement is not proof of indexing or durable storage in the final platform. Partially rejected batches are not automatically replayed. Monitor Collector/backend rejection diagnostics.
    • Coverage: the journal protects successfully persisted events; it is not a transactional audit trail and cannot guarantee an event for every operation.
    • Capacity and latency: persistence adds database load and latency. The backlog is not capped or automatically purged. Size database storage and recovery throughput for expected event rates and outage duration.
    • Storage protection: database durability, replication and backups remain essential. Protect journal payloads using the same access and retention controls as operational logs. Successfully acknowledged events are deleted; this table is not a permanent history archive.

    Monitor pending count and oldest admission time through Admin Tasks → Operational Event Journal. For a local Docker Collector that prints received records, use make start-otel and make logs-otel; an optional Eclipse launch group starts it before debugging the Master. See Local OpenTelemetry and journal testing.

    Alert on growing backlog age/count, journal/export error messages, database disk space and rejected records downstream. Do not routinely delete unacknowledged rows: doing so intentionally discards events. A local Collector with persistent queues remains useful to protect the next hop after the journal receives an OTLP acknowledgement.

    The Monitor page shows pending count, oldest admission timestamp and age, in-flight records, last successful persistence, last endpoint acknowledgement, and persistence/delivery failure history. It refreshes every 30 seconds by default, with manual refresh and an option to disable automatic refresh. Warning and critical thresholds are configurable with journalWarningPendingCount, journalCriticalPendingCount, journalWarningOldestAgeMillis and journalCriticalOldestAgeMillis in [OperationalEvents]; changes require a Master restart. Both count and oldest-age thresholds can trigger an alert.

    Administrators can pause or resume native event collection independently from delivery. Pausing collection does not change the splunk.log output and does not stop delivery of already-journalled events. Pausing delivery continues database admission, so the backlog can grow; a batch already in flight may complete. The runtime controls are audited and reset when the Master restarts. The page displays a browser-local backlog trend. It estimates drain time only after at least four queue samples spanning two minutes show a healthy decrease of at least two events; treat the estimate as an extrapolation, not a guarantee.

    Persistence failures highlight the Admin Tasks card, home-page and administration menu entries, with a banner on the home and Admin Tasks pages. Red means persistence has failed without a successful admission confirming recovery, or the worker is stopped. After persistence recovers, a yellow warning retains the failure count for the rest of the Master process. Runtime counters reset on Master restart; persisted pending rows do not. Export failures also produce an attention indicator. Detailed exceptions remain in service logs; payloads and credentials are not shown.

    The task is greyed out when journaling is disabled on the Master. Disabled journaling can still leave pending rows in the database. A Master connection failure is shown as unavailable. The page is read-only for event data: it does not expose payloads, purge records or force retries.

    The publisher exports the seven categories listed below. Operational events and the Monitor's database change log are separate records.

    Event Categories¶

    OpenECPDS generates various types of events, each categorised based on the nature of the operation being recorded:

    Code Category Description Fields
    PRS PRoduct Status Tracks the status of products as they progress through OpenECPDS. The system maintains a top-level monitoring display, which can be updated using the ecpds command. Events are logged at key stages, including when a set of files is scheduled, when files start being registered, and when they are fully recorded. PRS fields
    RET RETrieval Records a successful retrieval by the Retrieval Scheduler. Failed retrievals do not emit RET events; when tracing is enabled, their failed Mover attempts are visible in retrieval traces. RET fields
    UPH UPload History Records events whenever a file is successfully disseminated from OpenECPDS to a remote site. Tracks outbound file transfers. UPH fields
    INH INcoming History Logs incoming data transfers — files pushed to OpenECPDS or retrieved by users via the data portal. INH fields
    ERR ERRor Captures error events, specifically when a file fails to be disseminated successfully. ERR fields
    CPY CoPY / Replication Tracks file replication between different data movers. Records whether the replication was successful. CPY fields
    DEA DEnied Access Captures unauthorised access attempts, helping administrators identify security threats, misconfigurations, or unexpected behaviour. DEA fields

    Field formats¶

    Each event logged by OpenECPDS follows a structured format, with fields that provide detailed information about the recorded operation. The fields vary depending on the event category, capturing relevant attributes such as timestamps, file identifiers, processing statuses, and transfer details.

    Note

    All duration values are measured in milliseconds. Timestamps in the legacy Splunk output and timestamp-valued attributes are formatted in the Master JVM's default timezone, without an explicit offset. All timestamps are formatted as yyyy-MM-dd HH:mm:ss.fffffffff, where yyyy is the 4-digit year, MM is the 2-digit month, dd is the 2-digit day, HH is the 2-digit hour (24-hour clock), mm is minutes, ss is seconds, and fffffffff represents fractional seconds in nanoseconds. OpenTelemetry's top-level log timestamp is an absolute instant; use it for timezone-independent correlation. The examples assume the Master JVM uses UTC.

    Note

    A TimeStamp field is included in all Splunk log entries to ensure log rotation is correctly detected. This prevents Splunk from misidentifying rotated files due to identical file headers and avoids missing or duplicated log events.
